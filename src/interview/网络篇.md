# 网络安全篇

## XSS 分为哪几类?

根据攻击的来源，XSS 攻击可分为存储型、反射型和 DOM 型三种。

### 存储型 XSS

存储型 XSS 的攻击步骤：

1. 攻击者将恶意代码提交到目标网站的数据库中。
2. 用户打开目标网站时，网站服务端将恶意代码从数据库取出，拼接在 HTML 中返回给浏览器。
3. 用户浏览器接收到响应后解析执行，混在其中的恶意代码也被执行。
4. 恶意代码窃取用户数据并发送到攻击者的网站，或者冒充用户的行为，调用目标网站接口执行攻击者指定的操作。

这种攻击常见于带有用户保存数据的网站功能，如论坛发帖、商品评论、用户私信等。

### 反射型 XSS

反射型 XSS 的攻击步骤：

1. 攻击者构造出特殊的 URL，其中包含恶意代码。
2. 用户打开带有恶意代码的 URL 时，网站服务端将恶意代码从 URL 中取出，拼接在 HTML 中返回给浏览器。
3. 用户浏览器接收到响应后解析执行，混在其中的恶意代码也被执行。
4. 恶意代码窃取用户数据并发送到攻击者的网站，或者冒充用户的行为，调用目标网站接口执行攻击者指定的操作。

例如：用户点击一个搜索结果链接，该链接的 URL 中包含了搜索的词汇。如果应用不正确地处理输入参数，搜索词汇可能会被包含在 HTML 中返回给用户，从而执行嵌入的恶意代码。

反射型 XSS 跟存储型 XSS 的区别是：存储型 XSS 的恶意代码存在数据库里，反射型 XSS 的恶意代码存在 URL 里。

反射型 XSS 漏洞常见于通过 URL 传递参数的功能，如网站搜索、跳转等。

由于需要用户主动打开恶意的 URL 才能生效，攻击者往往会结合多种手段诱导用户点击。

POST 的内容也可以触发反射型 XSS，只不过其触发条件比较苛刻（需要构造表单提交页面，并引导用户点击），所以非常少见。

### DOM 型 XSS （不需要服务端参与）

DOM 型 XSS 的攻击步骤：

1. 攻击者构造出特殊的 URL，其中包含恶意代码。
2. 用户打开带有恶意代码的 URL。
3. 用户浏览器接收到响应后解析执行，前端 JavaScript 取出 URL 中的恶意代码并执行。
4. 恶意代码窃取用户数据并发送到攻击者的网站，或者冒充用户的行为，调用目标网站接口执行攻击者指定的操作。

DOM 型 XSS 跟前两种 XSS 的区别：DOM 型 XSS 攻击中，取出和执行恶意代码由浏览器端完成，属于前端 JavaScript 自身的安全漏洞，而其他两种 XSS 都属于服务端的安全漏洞。

例如：用户点击一个链接，链接的 URL 中包含了一个 hash 值（#后面的值）。页面的 JavaScript 可能会从 hash 值读取数据并将其插入到页面中，如果页面 JavaScript 未对这部分数据进行安全处理，则恶意代码就可能会被执行。

## 如何预发 XSS

XSS 攻击有两大要素：

- 攻击者提交恶意代码。
- 浏览器执行恶意代码。

### 预防反射型跟存储型

#### 过滤攻击者输入

使用 escapeHTML 函数，将<、>等转义成字符实体后存储，在用游览器就能正常展示。

#### 防止游览器执行恶意代码

1、使用纯前端渲染，通过 js 告诉游览器这是一段文本，如使用 .innerText 插入等
2、如果拼接 html 是必要的，就需要采用合适的转义库，对 HTML 模板各处插入点进行充分的转义

### 预防 DOM 型

DOM 型 XSS 攻击，实际上就是网站前端 JavaScript 代码本身不够严谨，把不可信的数据当作代码执行了。

在使用 .innerHTML、.outerHTML、document.write() 时要特别小心，不要把不可信的数据作为 HTML 插到页面上，而应尽量使用 .textContent、.setAttribute() 等。

### 其他 XSS 防范措施

1、严格的 CSP 在 XSS 的防范。

- 禁止加载外域代码，防止复杂的攻击逻辑。
- 禁止外域提交，网站被攻击后，用户的数据不会泄露到外域。
- 禁止内联脚本执行（规则较严格，目前发现 GitHub 使用）。

2、输入内容长度控制、输入校验
3、HTTP-only Cookie: 禁止 JavaScript 读取某些敏感 Cookie，攻击者完成 XSS 注入后也无法窃取此 Cookie。

## csrf

前置知识：Cookies 被设计为一种机制，允许服务器存储信息在用户的浏览器中，并且在用户之后的每次请求中，浏览器都会自动将这些信息发送回服务器（属于同一域）。这种行为是为了支持无状态的 HTTP 协议下的用户会话管理。

CSRF（Cross-site request forgery）跨站请求伪造：攻击者诱导受害者进入第三方网站，在第三方网站中，向被攻击网站发送跨站请求（该请求一般是跨域的）。利用受害者在被攻击网站已经获取的注册凭证，绕过后台的用户验证，达到冒充用户对被攻击的网站执行某项操作的目的。

一个典型的 CSRF 攻击有着如下的流程：

- 受害者登录 a.com，并保留了登录凭证（Cookie）
- 攻击者引诱受害者访问了 b.com
- b.com 向 a.com 发送了一个请求：a.com/act=xx 浏览器会默认携带 a.com 的 Cookie
- a.com 接收到请求后，对请求进行验证，并确认是受害者的凭证，误以为是受害者自己发送的请求
- a.com 以受害者的名义执行了 act=xx
- 攻击完成，攻击者在受害者不知情的情况下，冒充受害者，让 a.com 执行了自己定义的操作

CSRF 的特点

- 攻击一般发起在第三方网站，而不是被攻击的网站。被攻击的网站无法防止攻击发生。
- 攻击利用受害者在被攻击网站的登录凭证，冒充受害者提交操作；而不是直接窃取数据。
- 整个过程攻击者并不能获取到受害者的登录凭证，仅仅是“冒用”。
- 跨站请求可以用各种方式：图片 URL、超链接、CORS、Form 提交等等。部分请求方式可以直接嵌入在第三方论坛、文章中，难以进行追踪。

解决方法  
1、尽量使用 post  
2、加入验证码（就是用户验证码，移动滑块，点击文字等各种，确保是真人）或者再次输入密码  
3、验证 referer，进行同源检测  
4、CSRF Token  
5、Samesite Cookie 属性

SameSite Cookie 属性是一个用于防止跨站请求伪造（CSRF）攻击的安全功能。它允许服务器指定 Cookie 不应该随着来自第三方网站的请求一起发送。SameSite 属性可以设置为以下三个值之一，以控制 Cookies 的发送行为：

Strict（严格）:  
SameSite=Strict 属性会极限制 Cookie 的发送。当设置为 Strict 时，Cookie 仅在当前网站的请求中被发送，即只有当请求的域与 Cookie 的域完全匹配时，浏览器才会包含这个 Cookie。
这意味着即使用户通过点击链接从其他站点导航到使用了 SameSite=Strict 的网站上，也不会发送 Cookie。这种限制在保护用户免受 CSRF 攻击方面非常有效，但可能影响用户体验，因为一些基于 Cookie 的跨站点功能（如单点登录）将无法工作。  
Lax（宽松）:  
SameSite=Lax 提供了一种平衡方式，某些跨站点请求将允许发送 Cookie，具体取决于请求类型和用户的操作。通常，只有当用户从第三方网站导航到设置了 SameSite=Lax Cookie 的网站时(比如通过点击链接)以及请求是 GET 方法时，Cookie 才会被包含送出。
这对于防范 CSRF 攻击仍然很有效，同时允许了一些无害的跨站点请求（如导航）能够正常工作，提供了更好的用户体验。  
None（无）:  
SameSite=None 属性使得 Cookie 在所有的跨站点请求中都会被发送。为了设置 SameSite=None，Cookie 还需要设置 Secure 属性，表示 Cookie 仅在安全上下文中（如 HTTPS 协议）被发送。  
这对于那些需要在多个不同域之间共享 Cookie 的应用非常有用，例如，在内容分发网络(CDN)或是 SaaS 应用中提供跨域认证服务的场景。

## HTTP 和 HTTPS 协议的区别

1、HTTPS 协议需要 CA 证书，费用较高；而 HTTP 协议不需要。（费用）  
2、HTTP 协议连接很简单，是无状态的；HTTPS 协议是有 SSL 和 HTTP 协议构建的可进行加密传输、身份认证的网络协议，比 HTTP 更加安全（连接方式）。  
3、建立连接速度。（速度）  
4、HTTP 协议是超文本传输协议，信息是明文传输的，HTTPS 则是具有安全性的 SSL 加密传输协议（安全）。  
5、使用不同的连接方式，端口也不同，HTTP 协议端口是 80，HTTPS 协议端口是 443（端口）。

## https

HTTPS 经由 HTTP 进行通信，利用 SSL/TLS 来加密数据包。HTTPS 的主要目的是提供对网站服务器的身份认证，保护交换数据的隐私与完整性。
1、不只用对称加密，因为不可能保存一万个客户端的对称密钥
2、不只用非对称加密，因为非对称加密特别慢

验证证书的方式：  
首先使用一种 Hash 算法来对公钥和其他信息进行加密，生成一个信息摘要，然后让有公信力的认证中心（简称 CA ）用它的私钥对消息摘要加密，形成签名。最后将原始的信息和签名合在一起，称为数字证书。当接收方收到数字证书的时候，先根据原始信息使用同样的 Hash 算法生成一个摘要，然后使用公证处的公钥来对数字证书中的摘要进行解密，最后将解密的摘要和生成的摘要进行对比，就能发现得到的信息是否被更改了。

# http 状态码
# 0 背景
最近在工作中会有意无意的遇到各种有关 http 网络请求状态码的问题，如：接口 http 200 成功返回，但是返回报文体中却返回300（http 300 状态码是表示有多个资源可供游览器选择），产生歧义；以及在前端性能优化的 103 206 226 等等，然而目前 ATA 里的文章以及其他平台上的相关文章要么是状态码只列出一些重要的http状态码，要么就是只罗列状态码，无相关例子帮助理解跟解释这个状态码到底是用来做什么的。所以特意在工作之余，整合一篇文章来详细具体讲讲 HTTP 状态码的那些事。

# 1 什么是状态码
HTTP 响应状态码用来表明特定 HTTP 请求是否成功完成。 响应被归为以下五大类：
1、信息响应 (100–199)
2、成功响应 (200–299)
3、重定向消息 (300–399)
4、客户端错误响应 (400–499)
5、服务端错误响应 (500–599)

## 1.1 1xx Informational
**100 Continue** 
**含义：**服务器已收到浏览器的请求标头，并且现在已准备好发送请求正文。
**解释：**这使得请求过程更加高效，因为它可以防止浏览器发送正文请求，即使标头已被拒绝。

**101 Switching Protocols**
**含义：**服务器已经接受了客户端的请求，并将通过 Upgrade 消息头通知客户端采用不同的协议来完成这个请求。
**解释：**在发送完这个响应最后的空行后，服务器将会切换到在 Upgrade 消息头中定义的协议。

**102 Processing**
**含义：**服务器已经收到并正在处理请求，目前还没有响应。
**解释：**这样可以防止客户端超时，并假设请求丢失。

**103 Early hints**
**含义：**在服务器响应的 HTTP 消息之前返回一些响应头。该状态码用于允许用户代理预加载资源，同时服务器准备响应。
**解释：**HTTP 103 状态码 (Early Hints) 是一个信息性 HTTP 状态代码，可以用于在最终响应之前发送一个初步的 HTTP 响应。
利用 HTTP 103 状态码，就可以让服务器在服务器处理主资源的同时向浏览器发送一些关键子资源（JavaScript、CSS 或字体文件）或页面可能使用的其他来源的提示。
浏览器可以使用这些提示来预热连接，并在等待主资源响应的同时请求子资源。换句话说，Early Hints 可以通过提前做一些工作来帮助浏览器利用这种 服务器思考时间，从而提升页面的渲染性能。
（有点像 http2 的 Server Push 即在浏览响应 HTML 文件的时候，服务器会同时将所需的资源文件主动推送给浏览器。浏览器在收到推送的资源之后会缓存到本地。等解析 HTML 发现需要加载对应资源的时候会直接从本地读取，不必再等待网络传输了。虽然这听起来很神奇，但这个方案有非常大的缺陷：Server Push 很难避免推送浏览器已经拥有的子资源，其实很多资源在浏览器第一次请求到就已经缓存下来了。这种 “过度推动” 会导致网络带宽的使用效率降低，从而显着阻碍性能优势。总体而言，Chrome 数据显示 HTTP2/Push 实际上对整个网络的性能产生了负面影响。
所以，Chrome 宣布移除了对 HTTP/2 Server Push 特性的支持。）

## 1.2 2xx Success
**200 OK**
**含义：**表示客户端发来的请求被服务器端正常处理了。
**解释：**从 SEO 的角度来看，200 OK 状态码是功能页面的完美状态码，所有链接页面都在正常工作。200 表示搜索引擎爬虫可以成功爬取该页面并将其放入其搜索引擎中。

**201 Created**
**含义：**服务器完成了浏览器的请求，因此创建了一个或多个新资源。
**解释：**一般用以 POST 请求，代表服务器资源创建成功。如在 Github 中，创建 Issue 成功，则返回一个 201 的状态码。

**202 Accepted**
**含义：**服务器已接受浏览器的请求，但仍在处理中。该请求最终可能会也可能不会进行响应。
**解释：**这种就比较适合异步操作了，不需要客户端等待操作完成，直接返回给客户端信息。从这里也可以看到2**的请求服务器并不一定会处理成功

**203 Non-authoritative Information**
**含义：**使用代理时可能会出现此状态代码。这意味着代理服务器从源服务器收到了 200 状态代码，但在将响应传递给浏览器之前已对其进行了修改。
**解释：**表示返回的实体头部元信息不是在原始服务器上有效的确定集合，而是来自本地或者第三方的拷贝。当前的信息可能是原始版本的子集或者超集。

**204 No Content**
**含义：**该状态码表示客户端发送的请求已经在服务器端正常处理了，但是没有返回的内容，响应报文中不包含实体的主体部分。一般在只需要从客户端往服务器端发送信息，而服务器端不需要往客户端发送内容时使用。
**解释：**如 DELETE 请求成功后就是没有实际返回的内容

**205 Reset Content**
**含义：**服务器端成功处理了请求，且没有返回任何内容。但是与 204 响应不同，返回此状态码的响应要求请求者重置文档视图。该响应主要是被用于接受用户输入后，立即重置表单，以便用户能够轻松地开始另一次输入。
**解释：**请求后重置文档视图（不只是重置 from 表单）此响应旨在支持一个通用的数据录入用例 - 用户接收所支持的数据输入（表单，记事本，画布等）的内容，输入或操作该空间中的数据，使输入的数据在请求中被提交，然后为下一个条目重置数据输入机制，以便用户可以容易地启动另一个输入动作。
由于 205 状态码意味着不会提供额外的内容，所以服务器不应该在 205 响应中生成有效载荷。换句话说，服务器必须为 205 响应执行以下操作之一：
    a）通过包含一个值为 0 的 Content-Length 头字段来指示响应的零长度主体; 
    b）通过包括具有分块值的传送编码头部字段和由零长度的单个块组成的消息体来指示响应的零长度有效载荷; 或者，c）在发送结束报头部分的空白行之后立即关闭连接。

**206 Partial Content**
**含义：**该状态码表示客户端进行了范围请求，而服务器端执行了这部分的 GET 请求。响应报文中包含由 Content-Range 指定范围的实体内容
**解释：**一般用于视频或者图片资源的请求，如果整个文件过大可以先请求一部分，再接着请求下一部分，优化用户体验。

**226 IM Used**
**含义：**服务器已成功处理浏览器的 GET 方法，以检索已缓存资源的更新版本。通常，当请求的资源有一个或多个轻微修改时返回响应。
**解释：**在实践中，226状态码用于优化客户端与服务器之间的通信，当客户端已经有一个资源的先前版本时，服务器可以只发送自上次请求以来资源发生变化的部分。这可以减少网络带宽的使用，并提升性能。
总结来说，状态码226 "IM Used" 出现在提供响应增量更新的上下文中，这是为了让客户端更新它那边的缓存版本，而不是下载整个新资源。

## 1.3 3xx Redirection
**300 Multiple Choices**
**含义：**有时，服务器可能会响应多种可能的资源来满足浏览器的请求。
**解释：**300 状态码意味着浏览器现在需要在它们之间进行选择。当有多个可用的文件类型扩展名时，可能会发生这种情况。
在实际使用中，状态码 300 的行为并不像其他重定向状态码那样清晰，因为它不会指定一个明确的重定向目标。相反，它提供了一个资源列表给用户，让用户可以选择。虽然这个响应码定义了一个具有用户交互元素的重定向方案，但在实际应用中它并不常用。

**301 Moved Permanently**
**含义：**已为目标资源分配了一个新的永久 URI。
**解释：**新的 URI 会在 HTTP 响应头中的 Location 首部字段指定。若用户已经把原来的URI保存为书签，此时会按照 Location 中新的URI重新保存该书签。同时，搜索引擎在抓取新内容的同时也将旧的网址替换为重定向之后的网址。


**302 Found**
**含义：**请求的资源被分配到了新的 URI，希望用户（本次）能使用新的 URI 访问资源。
**解释：**和 301 Moved Permanently 状态码相似，但是 302 代表的资源不是被永久重定向，只是临时性质的。也就是说已移动的资源对应的 URI 将来还有可能发生改变。


**303 See Other**
**含义：**由于请求对应的资源存在着另一个 URI，应使用 GET 方法定向获取请求的资源。
**解释：**303 状态码和 302 Found 状态码有着相似的功能，但是 303 状态码明确表示客户端应当采用 GET 方法获取资源。303 状态码通常作为 PUT 或 POST 操作的返回结果，它表示重定向链接指向的不是新上传的资源，而是另外一个页面，比如消息确认页面或上传进度页面。而请求重定向页面的方法要总是使用 GET。

  * 当 301、302、303 响应状态码返回时，几乎所有的浏览器都会把 POST 改成GET，并删除请求报文内的主体，之后请求会再次自动发送。
  * 301、302 标准是禁止将 POST 方法变成 GET方法的，但实际大家都会这么做。

**304 Not Modified**
**含义：**浏览器缓存相关。该状态码表示客户端发送附带条件的请求时，服务器端允许请求访问资源，但未满足条件的情况。
**解释：**304 状态码返回时，不包含任何响应的主体部分。304 虽然被划分在 3XX 类别中，但是和重定向没有关系。

**305 Use Proxy**
**含义：**服务器需要代理才能返回请求的资源。此响应代码当前未使用，因为当前大多数浏览器由于安全问题不支持它。
**解释：**HTTP状态码305 "Use Proxy" 指示请求的资源必须通过代理才能被访问。状态码305响应必须包含一个用于访问请求资源的代理服务器的URI，格式通常是 "Location" 头部。客户端应配置其自身以发送后续对原始资源URI的请求到该代理。
这是以前用来通知客户端应该使用代理进行某些特定的请求的方法。然而，由于安全原因，305状态码已经不被推荐使用，并且现代浏览器也不支持这个响应状态码。
状态码305的一个重要细节是，客户端不应该自动切换到代理，它应该提示用户去设置代理，因为这可能会影响用户的网络安全和隐私。

**307 Temporary Redirect**
**含义：**类似于302，但要求客户端对新URI使用与原始请求相同的方法。
**解释：**这意味着如果原请求是POST，重定向的请求也必须是POST。

**308 Permanent Redirect**
**含义：**类似于301，但也要求客户端对新URI使用与原始请求相同的方法。
**解释：**相比于301，这个状态码明确了不允许改变方法，如果原请求是POST，重定向的请求也必须是POST。

总的来说，301和302状态码在历史上因为对方法的处理不够明确而引入了307和308状态码。307和308解决了这个问题，保证重定向时不会改变请求方法，从而解决了与早期303状态码类似的问题。如果你想保证在客户端和服务器间的通信中保持请求的方法不变，应该使用307或308而不是301或302。

## 1.4 4xx Client Errors
**400 Bad Request**
**含义：**请求报文中存在语法错误。
**解释：**当错误发生时，需修改请求的内容后再次发送请求。

**401 Unauthorized**
**含义：**发送的请求需要有通过 HTTP 认证(BASIC 认证、DIGEST 认证)的认证信息。若之前已进行过一次请求，则表示用户认证失败。
**解释：**返回含有 401 的响应必须包含一个适用于被请求资源的 WWW-Authenticate 首部用以质询(challenge)用户信息。当浏览器初次接收到 401 响应，会弹出认证用的对话窗口。

**402 Payment Required**
**含义：**为数字支付系统保留的。不过，它并没有被广泛使用。

**403 Forbidden**
**含义：**客户端请求已被拒绝，因为客户端无权访问内容。
**解释：**返与 401 不同，服务器知道客户端的身份，但由于他们无权查看内容，因此服务器拒绝提供正确的响应。

**404 Not Found**
**含义：**服务器上无法找到请求的资源。除此之外，也可以在服务器端拒绝请求且不想说明理由时使用。
**解释：**如：客户端请求的 URL 在服务器上不存在；客户端访问了一个已删除或从未存在的页面。

**405 Method Not Allowed**
**含义：**服务器识别到浏览器使用的 HTTP 请求方法，但需要使用不同的方法才能提供所需的资源。服务器应该总是允许客户端使用 GET 和 HEAD 方法进行访问。
**解释：**客户端可以通过 OPTIONS 方法（预检）来查看服务器允许的访问方法, 如下：
Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE

**406 Not Acceptable**
**含义：**服务器通知客户端没有资源符合浏览器请求的标准。
**解释：**与 404 不同的是，406 表示请求的资源不能以客户端指定的条件返回，即服务器无法提供符合 Accept 头部条件的响应（不能满足请求报文头中的条件）。服务器找到了资源，但资源与客户端要求的不匹配（例如，内容类型、编码、语言）。

**407 Proxy Authentication Required**
**含义：**表示客户端必须先经过代理服务器的认证，然后请求才能被代理服务器转发到最终的目的服务器。
**解释：**401 Unauthorized：由最终目的服务器返回，表示客户端的认证信息无效或者不存在，要求客户端提供有效的认证信息来访问资源。407 Proxy Authentication Required：由代理服务器返回，表示客户端需要通过代理服务器的认证来将请求转发到最终目的服务器。
这两种状态码用来处理不同的认证场景，了解它们有助于调试与身份认证相关的网络问题，以及设计相关认证机制的系统。

**408 Request Timeout**
**含义：**当服务器在等待来自浏览器的完整请求时超时时会生成此状态码。换句话说，客户端启动了一个请求，但迟迟未能发送完整的请求数据，导致服务器在等待过程中超时并返回 408 状态码。
**解释：**这种情况可能出现在一些网络延迟较大的环境中或客户端由于某些原因（如处理慢、带宽小等）发送请求数据较慢。
在高并发的环境下，服务器资源非常宝贵。408 状态码可以防止服务器因为等待某个客户端的请求时间过长而浪费资源。
服务器可以在预设的超时时间内没有收到完整请求时，返回 408 并关闭连接。这可以让服务器更快地恢复处理其他客户端的请求。（防止服务器资源长时间占用）

**409 Conflict**
**含义：**用于表示客户端请求与服务器的当前状态存在冲突，导致请求无法被处理。这个状态码通常在以下几种冲突场景中使用
**解释：**
* 资源的并发修改冲突
当多个客户端尝试同时修改同一个资源时，可能会引发冲突。服务器使用 409 状态码通知客户端，资源冲突需要解决。
* 资源的状态冲突
请求的操作与资源当前的状态不一致，导致不能完成请求。例如，尝试删除一个不存在的文件或目录。
* 处理创建资源的冲突（如重复的唯一键）
如果客户端尝试创建一个资源时，使用了一个已经存在的唯一标识符（如数据库中的主键），也可能导致 409 冲突。
* 高级应用：基于Etag的并发控制
在一些情况下，为了避免并发冲突，可以使用 Etag 或者 If-Match 请求头来实现乐观锁定。

**410 Gone**
**含义：**状态码表示客户端请求的资源曾经存在，但现在已经永久性地不存在。服务器明确告知客户端，该资源不会再提供，因此客户端无需再尝试请求该资源。
**解释：**与 404 不同的是，404 表示资源未找到，但不指明资源是否曾经存在，常用于未知状态的资源请求。而 410 常用于资源已被永久性删除的情况。例如，删除了无用或不再适用的内容，通知客户端不要再尝试访问该资源。 

**411 Length Required**
**含义：**表示服务器在接收到客户端的请求时，发现请求缺少必要的 Content-Length 头，从而拒绝处理该请求。这个状态码通常用于需要明确知道请求主体长度的场景，如某些需要验证请求大小的操作。
**解释：**如：假设客户端试图上传一个文件或提交一个表单，但未提供 Content-Length 头部；在处理比较复杂的数据传输操作时，服务器可能期望在开始处理内容之前知道其大小，从而决定缓存策略或者是否接收该请求。这种情况下，缺少 Content-Length 头部无法满足服务器的需求。 

**412 Precondition Failed**
**含义：**表示客户端在请求中设置的某些前置条件未得到满足，导致服务器拒绝处理该请求。通常，客户端使用某些头部字段（如 If-Match、If-Unmodified-Since、If-None-Match 和 If-Modified-Since）来对请求进行条件化处理，如果这些条件中的任何一个未被满足，服务器会返回 412 状态码。
**解释：**
* 常见头部字段
If-Match: 请求方法通常用于修改资源（如 PUT、PATCH），当条件为真时执行操作。条件不满足时（例如 ETag 不匹配），返回 412 状态码。
If-Unmodified-Since: 检查资源是否自特定时间以来未被修改。用于避免在被修改的资源上执行不期望的操作。
If-None-Match: 通常用于避免重复的 GET 请求，或者条件 DELETE 操作。如果 ETag 符合指定条件，则不会执行请求。在修改资源请求中，如果条件满足，返回 412 状态码。
If-Modified-Since: 检查资源自特定时间后是否被修改。用于条件 GET 请求，以减少不必要的数据传输。

304 Not Modified 用于 GET 请求条件验证，确认本地缓存是否有效。
412 Precondition Failed 用于更新或删除操作，确保前置条件（如 ETag 或最后修改时间）满足以避免并发冲突。
希望这样能更清楚地解释它们的区别，以及在各自使用场景中的作用。
如：某次请求携带 ETag 想进行更新资源的操作，但是服务端的最新资源的 ETag 已经变了，这个时候就会告知客户端， ETag 不符合要求，不允许更新。

**413 Payload Too Large**
**含义：**表示请求的大小超过了服务器愿意或能够处理的限度。服务器使用此状态码拒绝处理这个过大的请求。这个状态码在某些情况下非常有用，可以防止服务器资源的滥用和过载。
**解释：**如：文件上传超限，提示用户上传的文件过大，并建议上传较小的文件，或者分块上传文件；数据提交超限等场景。

**414 Request-URI Too Long**
**含义：**表示请求的 URI（包括路径和查询字符串）长度超过了服务器愿意处理的范围。因此，服务器拒绝处理该请求。
**解释：**这通常发生在客户端生成了一条非常长的 URL，超过了服务器的限制。

**415 Unsupported Media Type**
**含义：**请求已被服务器拒绝，因为它不支持请求数据的媒体格式。

**416 Requested Range Not Satisfiable**
**含义：**表示服务器无法满足客户端在请求中使用的 Range 头，因为请求的范围在目标资源的当前范围之外。通常用于处理部分内容请求（Partial Content Requests）。
**解释：**客户端请求了一个资源的部分内容，但请求的范围超出了资源的实际长度。例如，客户端请求第1000字节开始的一部分内容，但资源总长度只有900字节。

**417 Expectation Failed**
**含义：**服务器无法满足客户端在请求中的 Expect 首部字段所指定的期望值。这个状态码通常用于处理 Expect: 100-continue 头部字段。
**解释：**
* Expect: 100-continue 头部字段
客户端在发送大请求体（如文件上传）时，使用 Expect: 100-continue 头部字段可以先与服务器确认是否能够处理请求（如检查请求头部中的 Content-Length 是否在可接受的范围内，防止超大文件上传等。）。服务器会在确认可以处理后，返回 100 Continue 状态码，客户端再发送请求体。如果服务器预先确定请求无法处理，则返回 417，客户端无需发送请求体。

**421 Misdirected Request**
**含义：**表示请求被发送到了不应该处理该请求的服务器。服务器认为它没有是目标资源的正确 URI 权威，相应地拒绝处理该请求。此状态码通常用于代理服务器或负载均衡器之间的通讯。

**422 Unprocessable Entity（状态码通常用于 WebDAV）**
**含义：**表示服务器理解了请求的内容类型，但请求中的数据有逻辑或验证错误。客户端应根据返回的详细错误信息修正请求数据，服务器应确保返回清晰的错误反馈，帮助客户端正确地重新发送请求。
这种机制有助于实现客户端与服务器之间有效的数据传输和验证，提高系统的健壮性和用户体验。

**423 Locked（状态码通常用于 WebDAV）**
**含义：**表示被请求的资源当前被锁定。

**424 Failed Dependency（状态码通常用于 WebDAV）** 
**含义：**常用于 WebDAV 场景或其他涉及多个请求的操作链中。当某个请求依赖的前置请求失败时，服务器会返回 424 状态码。客户端应根据返回的错误信息，分析依赖关系，并在修正前置请求后重试当前请求。服务器需准确管理和反馈请求之间的依赖关系，方便客户端进行有效的错误处理和重试操作。

**426 Upgrade Required** 
**含义：**表示客户端应切换到另一个协议以完成请求。服务器可以在响应头中提示客户端使用某个特定的协议进行重试。
这个状态码通常用于促使客户端从一个较旧的协议版本升级到一个较新的、更安全或更高效的协议版本，例如从 HTTP/1.1 升级到 HTTP/2。
**解释：**101 表示服务器已经同意切换到客户端在请求中指定的协议。状态码 101 是服务器对 Upgrade 头部字段的一个直接响应，表示服务器已经开始使用新的协议。101 是客户端请求升级，服务器同意；而 426 是服务器要求升级，客户端响应。

**428 Precondition Required** 
**含义：**服务器需要请求在执行操作之前满足某个前置条件。这个状态码主要是为了避免失效的更新问题，即在没有进行任何条件检查的情况下，客户端可能覆盖掉其他客户端的修改。此状态码通常与 If-Match 或 If-Unmodified-Since 头部一起使用，它们确保资源的状态在被修改之前未发生变化。
**解释：**在分布式系统或多用户环境中，多个客户端可能同时访问和修改相同的资源。在这种情况下，为了避免数据冲突和覆盖，服务器可以要求客户端在修改资源时提供一定的前置条件，如 ETag 或时间戳。
用于要求客户端提供前置条件头部，以确保并发环境中的数据一致性和避免失效更新问题。它主要用于需要进行条件请求控制的场合，如资源修改或删除。
客户端在接收到 428 状态码时，应根据服务器的说明提供适当的前置条件头部，例如 If-Match 或 If-Unmodified-Since，以确保请求的条件一致性。服务器使用 428 状态码来强制客户端提供这些前置条件，从而有效管理资源的并发访问，确保数据的一致性和正确性

**429 Too Many Requests** 
**含义：**表示客户端在给定的时间段内发送了太多的请求，服务器因此拒绝处理请求。这通常用于实现限流机制，以保护服务器免受过载或恶意请求的攻击

**431 Request Header Fields Too Large** 
**含义：**用于指示客户端发送的请求头部字段过大，服务器无法处理。该状态码提高了服务的安全性和稳定性，特别是在防护超长请求头部攻击时。

**451 Unavailable For Legal Reasons** 
**含义：**表示服务器无法处理请求，因为所请求的资源不可用，通常是由于法律原因或者是法规要求导致的。这个状态码适用于内容被审查、被法律禁止访问或者因为版权等法律问题而无法提供的情况。

**499 Client closed request** 
**含义：**一个非标准的状态码，通常由 Nginx 服务器使用。此状态码表示客户端在服务器完全处理请求之前关闭了连接。该状态码有助于服务器和开发者了解请求被中断的原因，特别是在没有标准 HTTP 方法来表示客户端中断连接的情况下。

## 1.5 5xx Server Error
**500 Internal Server Error** 
**含义：**表示服务器在处理请求时遇到了意外的情况，这种状况阻止了服务器完成请求。这个状态码意味着服务器发生了错误，但没有详细的客户端指引信息，因此客户端只能知道有问题发生，但无法准确知道是什么问题。
**解释：**服务器在处理请求时遇到的未预见的内部错误。这种错误可能由于各种原因导致，如代码异常、资源不足、配置错误等

**501 Not Implemented** 
**含义：**表示服务器不支持请求方法，并因此无法处理请求。这个状态码通常用于指示服务器缺少处理请求所需的功能或能力。它表示服务器无法执行客户端所请求的方法，但这不一定意味着资源本身不可用。
**解释：**客户端发送使用未实现方法的请求：
```
PATCH /resource HTTP/1.1
Host: example.com
```

**502 Bad Gateway** 
**含义：**表示作为网关或代理的服务器从上游服务器接收到无效响应。这通常意味着网关或代理服务器无法从其尝试访问的源服务器（上游服务器、中间服务器等）获取可用的响应。
这个状态码的出现通常与服务器之间的通信问题有关，而不是客户端与服务器之间的直接通信问题。
**解释：**这种错误通常出现在负载均衡器、反向代理服务器或 API 网关等代理服务器无法正确连接或获取响应的情况下。

**503 Service Unavailable** 
**含义：**表示服务器当前无法处理请求。这个状态码通常用于暂时性的状况，例如服务器超载或正在进行维护。503 状态码通常建议客户端可以稍后重试，并可以通过 Retry-After 头部字段告知客户端可以重新尝试请求的时间。
**解释：**当服务器暂时性不可用（例如正在进行维护或由于流量高峰导致资源不足），可以返回 503 状态码，并建议客户端稍后重试请求。

**504 Gateway Timeout** 
**含义：**网关或者代理的服务器无法在规定的时间内获得想要的响应。
**解释：**代码执行时间超时；代码发生了死循环。

**505 HTTP Version Not Supported** 
**含义：**请求中使用的 HTTP 版本不受服务器支持。
**解释：**服务器不支持客户端请求中使用的 HTTP 版本。客户端在处理 505 状态码时，应检查并确保使用受支持的 HTTP 版本。服务器则应尽量支持更多常见的 HTTP 版本，并在返回 505 状态码时提供详细的错误信息。

**506 Variant Also Negotiates** 
**含义：**服务器内部配置错误。
**解释：**服务器存在内部配置错误：客户端请求的方法变体选择器 (Content Negotiation) 也在变体选择过程中使用了一个选择变体。简而言之，这意味着所请求的资源配置错误，导致循环引用，服务器无法确定适当的资源变体。
当服务器配置内容协商，并且在选择适当的资源变体时发现某个变体本身也是需要在内容协商过程中选择的变体，导致循环依赖时，可以返回 506 状态码。

**507 Insufficient Storage** 
**含义：**服务器无法存储完成请求所必须的内容。
**解释：**服务器无法存储完成请求所必须的内容。这个状态码通常在处理需要较大存储空间的请求（例如文件上传、数据存储等）时出现，表示服务器的存储空间已满或不足以完成请求。

**508 Loop Detected（状态码通常用于 WebDAV）** 
**含义：**服务器在处理请求时检测到无限循环。
**解释：**服务器在处理请求时检测到循环。这通常发生在 WebDAV（Web Distributed Authoring and Versioning）请求时，服务器发现一个无限循环导致无法完成请求。
这个状态码主要用于 WebDAV 扩展，而不是常规的 HTTP 请求。如果服务器在处理具体操作时（例如 PROPFIND、COPY、MOVE 请求）检测到循环引用，那么便会返回 508 状态码。

**510 Not Extended** 
**含义：**服务器需要进一步扩展请求才能完成。这个状态码通常用于表示客户端请求中缺少某些特定扩展项或功能，比如请求需要某些协议或功能扩展，服务器才能成功处理该请求。
**解释：**当客户端发送的请求缺少特定的扩展或功能（例如安全扩展或协议功能），服务器返回 510 状态码，告知客户端需要额外的扩展项才能完成请求。

**511 Network Authentication Required** 
**含义：**表示客户端需要进行身份验证才能获得网络访问权限。
**解释：**客户端需要进行身份验证才能获得网络访问权限。此状态码常用于公共 Wi-Fi、公司网络等需要进行身份验证的网络环境。
客户端在处理 511 状态码时，应根据服务器提供的提示访问指定的登录页面进行身份验证，并在完成验证后重试请求。服务器则需要配置强制门户，提供清晰的登录页面和指引，并记录和监控用户的身份验证情况，确保系统的安全性和用户的正常访问。
通过正确的配置和管理，能确保用户在需要进行身份验证的网络环境中顺利访问资源，同时提高系统的安全性和用户体验。

401 Unauthorized：用于应用层面的资源访问控制，需要提供应用层的身份验证凭据。
511 Network Authentication Required：用于网络层面的访问控制，需要进行网络登录或接受使用条款。

客户端处理方式：
401：请求新的或有效的身份验证凭据。通常通过提示用户输入用户名和密码，或者重新发送带有令牌的请求。
511：重定向到指定登录页面，进行网络层的身份验证或接受条款，然后重新尝试访问原始请求的资源。

服务器处理方式：
401：提供 WWW-Authenticate 头部字段，指明所需要的身份验证方法。
511：提供登录页面或相关网址，让用户进行网络身份验证。

## TCP
TCP为什么可靠？（拥塞控制、流量控制、重传机制、保证顺序机制、面向连接的）

TCP的重传机制
由于TCP的下层网络（网络层）可能出现丢失、重复或失序的情况，TCP协议提供可靠数据传输服务。为保证数据传输的正确性，TCP会重传其认为已丢失（包括报文中的比特错误）的包。TCP使用两套独立的机制来完成重传，一是基于时间，二是基于确认信息。
TCP在发送一个数据之后，就开启一个定时器，若是在这个时间内没有收到发送数据的ACK确认报文，则对该报文进行重传，在达到一定次数还没有成功时放弃并发送一个复位信号。

TCP的流量控制机制
一般来说，流量控制就是为了让发送方发送数据的速度不要太快，要让接收方来得及接收。TCP采用大小可变的滑动窗口进行流量控制，窗口大小的单位是字节。这里说的窗口大小其实就是每次传输的数据大小。
● 当一个连接建立时，连接的每一端分配一个缓冲区来保存输入的数据，并将缓冲区的大小发送给另一端。
● 当数据到达时，接收方发送确认，其中包含了自己剩余的缓冲区大小。（剩余的缓冲区空间的大小被称为窗口，指出窗口大小的通知称为窗口通告 。接收方在发送的每一确认中都含有一个窗口通告。）
● 如果接收方应用程序读数据的速度能够与数据到达的速度一样快，接收方将在每一确认中发送一个正的窗口通告。
● 如果发送方操作的速度快于接收方，接收到的数据最终将充满接收方的缓冲区，导致接收方通告一个零窗口 。发送方收到一个零窗口通告时，必须停止发送，直到接收方重新通告一个正的窗口。
